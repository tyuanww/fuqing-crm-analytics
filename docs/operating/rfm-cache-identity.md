# RFM 缓存查询身份

RFM 八象限缓存只复用同一实际查询窗口的结果。精确 key 未命中时，HTTP 保持 `503` 和 `Retry-After`，不在请求中同步跑三段 RFM，也不以邻近日期的数字代替。

## Key 的字段

`backend/services/health/rfm_analysis/_shared.py` 的 `_cache_key()` 是缓存身份的维护源，包含以下字段。

- 查询策略版本 `rfm-exact-window-v1`。
- 数据版本，即 `orders.max(pay_time)`。
- 实际当前期开始、结束日期。
- 渠道、指标与排序后的排除渠道摘要。
- 实际比较期开始、结束日期。内部生产者未提供比较期时，按同窗口的默认同比补齐。
- 实际第三期开始、结束日期。内部生产者未提供第三期时，按同窗口前推两年补齐。

当前期、比较期和第三期全部相同的 period 别名使用同一个 key。默认和显式提供的等价日期可以共用结果，任意一期不同都不能混用。`analysis.get_rfm_analysis()` 继续使用既有日期解析器的优先级，将三组实际范围同时用于计算、缓存读取和写入，不把被忽略的原始参数写成缓存身份。

结果年份标签取自实际窗口的开始年份，与显式日期查询一致。跨年回看不使用今天的年份替代真实数据年份。

## 预计算边界

`rfm_dashboard_full` 快路径要求开始日和结束日都与请求相同。只有较早结束日的分区不算命中，随后沿既有计算路径处理。缓存层不再按前后两天或今天的 period 标签替换到另一日期窗口。

## 旧缓存与切换

旧查询口径产生的无版本 key 不被新服务复用。不因本次升级主动迁移或删除旧行。原有成功预热后的 48 小时 retention 规则不变，不承诺旧行永久保留。

切换新代码前需要按新 key 重新预热并验收。隔离验收使用新的独占缓存文件，不覆盖现役缓存，也不把旧回执或旧 payload 摘要当成新口径已计算的证明。

## 仍保留的限制

日期精确不代表数据最新。完整 active generation 的既有 last-known-good 策略保留，普通 on-demand 缓存继续检查版本、订单行数和 TTL。预热目录、近两年筛选覆盖、商品持久缓存以及查询结果的独立业务数值复核仍需各自验收。
