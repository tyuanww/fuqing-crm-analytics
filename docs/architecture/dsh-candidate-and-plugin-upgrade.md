# Why Harness upgrades and plugin updates use separate lanes

The platform has two moving parts. Harness owns the host, SDK, runtime, and plugin contracts. Plugins own business behavior. Keeping these changes in separate lanes makes upgrades easier to review and easier to undo.

## The problem

Replacing the host and changing a plugin in the same working tree hides the source of a failure. A peer mismatch, a missing runtime dependency, and a browser regression can all look like one broken application. A direct `latest` install also removes the exact bytes needed to reproduce or roll back the change.

## The approach

```text
official Harness tag
        │
        ▼
isolated candidate ── fixed profile ── plugin packs
        │                            │
        ├─ consumer closure           ├─ source/tree/tarball provenance
        ├─ browser and restart        └─ pack reader
        └─ fallback receipt
        │
        ▼
internal use or formally authorized release
```

The main checkout keeps its compatibility pin. A candidate records the upstream tag, source commit, toolchain, plugin pack inputs, and fallback. A plugin pack records its own source and generated bytes. The candidate consumes the pack as an artifact rather than reading a neighboring source checkout.

## Why the two lanes stay separate

The separation gives the maintainer four useful facts:

1. A Harness change can be tested with the existing plugin set.
2. A plugin change can be tested against the current Harness pin.
3. A failed candidate does not replace the usable runtime.
4. A rollback can name the exact previous bytes instead of guessing from a branch.

The cost is a little more preparation. The benefit is that an upgrade failure has one identifiable owner and one reproducible input set.

## What does not count as an upgrade

- Installing `latest` without recording a tag and digest.
- Reading a plugin from an ignored workspace.
- Treating a passing plugin unit test as host compatibility.
- Calling a local candidate receipt company release evidence.
- Reusing an old profile pack with a new Harness pin.
