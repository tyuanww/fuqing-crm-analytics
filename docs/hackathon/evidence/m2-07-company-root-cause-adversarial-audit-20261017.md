# M2-07 公司级根因与对抗审计（2026-10-17）

## 结论

当前最早的结构性问题不是缺少某个签名工具，也不是某个 alpha2/alpha4 测试失败，而是版本、插件包、宿主能力、Session 持久化和发布证明没有共享一份可执行的 runtime contract。每次失败后新增一个局部门禁，结果是本地技术证据越来越多，发布对象和信任边界仍然没有统一。

## 已确认的高风险

1. `scripts/release/plugin-pack.mjs:219-237` 只绑定 Git HEAD、tracked `package.json` 和 Git status；实际 `lib/` 被各插件 `.gitignore` 忽略。真实隔离复现中，未进入 Git 的 `plugin/lib/index.js` 被成功打包，回执仍为 `source_dirty=false`。这证明 source SHA 与 generated bytes 没有绑定，是 P0。
2. `scripts/release/runtime-bundle.mjs` 对 ignored/untracked runtime build outputs 也没有完整 tree digest，存在同类 bundle substitution 风险，是 P0。
3. release/preflight workflow 的 checkout 没有与 B0 workflow 一样显式 `persist-credentials:false`；reviewed source 执行期间可能接触 checkout token，是 P0。
4. 没有统一的 top-level release subject set，把 SDK、CRM、9 个 pack/profile、SBOM、graph、provenance 和 rc2 rollback 绑在一个不可变 manifest 上。
5. host capability 没有进入 plugin/profile contract；brand route、page-documents、board API、sessionQuery 和 preference gate 缺失时，安装可以通过，浏览器才暴露 pending/404。
6. history/recovery 过去混用手写 Session fixture 和外置 fixture 服务；只重启 host 不足以证明 storage、session lease 和 board service 恢复。
7. 当前 GitHub release workflow 是 rc2 专用，没有 alpha4/CRM consumer 的受保护发布流水线；owner key 或 cosign 本身不能补上这个缺口。
8. 单人 owner 的 replay 能证明可重复，不能证明独立批准；GitHub environment 的 self-review 也不能当作独立验证。

## 顶尖团队会主动补的控制

- 先定义 threat model、发行类别和唯一 release subject set，再选签名工具。
- 用 ephemeral clean builder 重新生成所有 ignored outputs，并绑定 builder/toolchain/runner/tree digest。
- 把 host capabilities、Session V4、persisted formats、warm rollback 写成合同，而不是靠浏览器发现。
- 用 protected CI verifier、OIDC/KMS、immutable artifact store、DSSE/SLSA provenance、revocation/expiry 和 final attestation 形成完整信任链。
- 做 artifact swap、SBOM swap、旧 lock、错误 Cordis、缺 brand route、缺 page service、错误 callId、fixture 保留但 storage 重启等负测。
- 做 key rotation/revocation、registry 污染、runner token 泄漏和 warm rollback 演练。

## 公司级执行顺序

先建立 `runtime-contract/v1` 和 `release-subject-set/v1`，再修 generated bytes provenance 与 release workflow token 边界；随后补 host capability/session/recovery 合同，最后建立 alpha4 受保护 pipeline 并重新运行 closure、SBOM、provenance、签名、撤销和 clean-machine。

单人公司可以没有第二位员工，但不能把 operator、builder、signer、verifier 和 registry 全部合成同一信任身份。内部 owner-operated 使用可以减少人员门禁；对外分发仍需要系统身份隔离和可撤销的公司信任根。

当前正式状态继续保持：`M2-07=BLOCKED`、`M2-08=NOT_RUN`、`release_ready=false`，主仓 DSH pin 仍为 `0.1.7-rc.2`。
